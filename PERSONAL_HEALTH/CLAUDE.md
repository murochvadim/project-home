# Personal Health

A **Personal Health Record** — a per-person body-metrics tracker. **Not a standalone agent**: it lives as the **Personal Health tab on the Medical page** (`medical.html`), reusing the Medical sidebar entry. Dashboard-only; no LXC service, no `agents`-table row.

## Status (2026-06-25)
**Shipped:** per-person **profile + weight log → BMI**, and a per-person **medications list** with a safety **ℹ️ Info window**.

**People come from the canonical `household_users` table** — the person dropdown is populated from `GET /api/household-users` (the Privacy → Settings → Users list, a real table since 2026-06-25 — REPLACED the old `dashboard_settings.privacy.users` JSON blob, which was deleted). No people are created here; each household member gets a body profile + logs. `ph_profiles.user_id` FKs to `household_users(id)` (resolution still also works by name during transition). If the list is empty the tab points the user to Privacy → Settings → Users.

**Profile** (slow-changing, per person): name, sex, date-of-birth, height, **allergies**, **conditions** (the last two feed the future cross-check). **Weight log** (time-series). **BMI / age / BMI-category / ideal-weight** are computed in the front-end (never stored — can't go stale when height/DOB are corrected).

**Medications** (per person): each pill **row** shows `name · dose · schedule` + Info/Edit/Stop/Del — the **basic info (name/dose/schedule/notes) is edited on the row**, exactly like a normal list. The **ℹ️ Info button** opens a window holding the **extra/safety info** (purpose, ingredients, drug_class, avoid_with, contraindications, side_effects, warnings, prescriber, started) with its **own edit** (`✎ Edit info`). The **schedule model** supports `daily` / `weekly` / `every_n_months` (e.g. 6 = half-year) / `every_n_days` / `once` / `as_needed`, with `times` (HH:MM, comma-sep), `dow`, `interval_n`, `next_due` — built so a **future reminder watcher** can compute each pill's next-due time. **Schedule cell rendering (2026-06-26):** `medSchedText(m, html)` formats the row's schedule; the **`next_due` date renders as `15 Nov 2026`** (via `_phFmtDate`, `toLocaleDateString` `en-GB` day/short-month/year — not ISO) and, in the table (`html=true`), as a **bigger green span** (`#1a7f37`, 0.92rem, bold, 8 px left-gap); the **ℹ️ Info** window uses the same function with `html` falsy → plain formatted text. Dynamic parts (`times`, `dow`) are HTML-escaped in `html` mode since the table cell isn't outer-`esc()`'d.

**Future med-safety cross-check (designed, schema is ready):** flag when a med's **`avoid_with`** / **`contraindications`** / **`ingredients`** conflict with the person's **`allergies` + `conditions`** or their **other active meds**. All the data is captured now; the flag itself is a later step. The UI is worded as a **record / reminder aid — not medical advice**.

**Deferred:** waist + waist-to-height, activity → BMR/TDEE, body-fat %, vitals (HR/BP), **progress charts** (Chart.js already loaded on the page), **goals & achievements**, and the **reminder watcher**. (**Daily steps shipped 2026-06-25** — manual + walking-trip import; see "Daily steps" below.) (`manufacturer` / `mechanism` were considered for meds and dropped — reference-only, not needed for the cross-check.)

## Tables (LXC 102, `home_data`)
- **`ph_profiles`** — one row per person: `id, name, sex ('male'|'female'), date_of_birth, height_cm, allergies, conditions, weight_sched, bp_sched, created_at, user_id`. **`user_id` FK → `household_users(id)` ON DELETE CASCADE** (the canonical member identity; backfilled by name 2026-06-25, `ph_profiles.name` kept for transition). **`weight_sched` / `bp_sched`** (JSONB, added 2026-06-26, migration `012_measure_schedule.sql`) — per-person **measure reminder schedule** for the Weight + BP cards: `{freq, interval_n}` or NULL=Off. `freq ∈ daily | weekly | every_n_days | every_n_months` (same options as meds **minus** weekday / day-of-month / time, per user); `interval_n` only for the `every_n_*` freqs. Capture-only today; a **future LXC-104 reminder watcher** will read these + the person's last weight/BP `measured_at` and flag "overdue" when nothing's logged within the window (no `next_due` stored — derived from the last reading). Retention: forever.
- **`ph_measurements`** — weight log: `id, profile_id (FK → ph_profiles ON DELETE CASCADE), measured_at (timestamptz, stamped server-side on Save — same style as BP, no manual date), weight_kg, created_at`. Indexed `(profile_id, measured_at DESC)`. Retention: forever (`auto_clean=false`).
- **`ph_medications`** — pills: `id, profile_id (FK ON DELETE CASCADE), name, dose, freq, interval_n, times, dow, next_due, notes, purpose, ingredients, drug_class, avoid_with, contraindications, side_effects, warnings, prescriber_id (→ medical_contacts), started_at, active, special_date, special_note, created_at`. Indexed `(profile_id)`. Retention: forever. **`special_date` (DATE) + `special_note` (TEXT)** (added 2026-06-26, migration `013_med_special_schedule.sql`) — an optional **"Special Schedule"** per med: a dated logistical task (order refill, arrange pre-injection authorisation doc, etc.). When any med has it set, the 💊 table shows a **"Special Schedule" column** (`date · special_note`) **colored by proximity** using the **shared project-wide "Schedule & appointment colors"** (`dashboard_settings.privacy.settings` `{red_days,yellow_days,grey_days}`, edited at **Privacy → Settings** — the SAME single config the Privacy appointment cards use; it's purely cosmetic, so one config serves the whole project). Band fn `_phApptBand` in `personal-health.js` is a copy of privacy.js `_pvApptBand` (medical.html doesn't load privacy.js); both read the same settings key, so editing the colors in Privacy recolors both. The Privacy card was relabeled **"Schedule & appointment colors"** to reflect the wider scope.
- **`ph_steps`** — daily step entries: `id, user_id (FK → household_users ON DELETE CASCADE — NOT profile_id; keyed by the person so walking-trip imports match), measured_at (timestamptz), steps (int), source ('manual'|'trip'), trip_id (bigint, phone_trips.id when source='trip'), created_at`. Indexed `(user_id, measured_at DESC)` + **partial UNIQUE `(trip_id) WHERE trip_id IS NOT NULL`** (a trip imported once). Migration `010_steps.sql`. Retention: forever.
- **`ph_body`** — waist & hip circumference log (cm): `id, profile_id (FK → ph_profiles ON DELETE CASCADE), measured_at (timestamptz, server-stamped on Save), waist_cm, hip_cm, created_at`. Indexed `(profile_id, measured_at DESC)`. **WHR (Waist-to-Hip Ratio = waist ÷ hip) is COMPUTED, never stored** — `GET /body` returns `round(waist_cm/NULLIF(hip_cm,0), 2) AS whr`, and the front-end recomputes the latest one for the summary chip. Migration `014_body.sql`. Retention: **forever + `protected=true`** (set directly in the migration — the one-time server.js protect-seed already fired via its sentinel). The per-person measure schedule lives on **`ph_profiles.body_sched`** (JSONB, same shape as `weight_sched`/`bp_sched`).

- **`ph_water`** — daily water intake: `id, profile_id (FK → ph_profiles ON DELETE CASCADE), measured_at (timestamptz, server-stamped on +1 cup), cups (numeric, default 1), created_at`. Indexed `(profile_id, measured_at DESC)`. Migration `015_water.sql`. Retention: **forever + `protected=true`**. The goal is **GLOBAL** in `dashboard_settings.medical.water` `{enabled, target, start_hm, end_hm, interval_min}` (edited on **Medical → Settings → 💧 Water**) — one household goal/window/interval; each person logs their own cups against it. (`ph_profiles.water_sched` from migration 015 is **unused** — the goal moved global; the column is left in place, harmless.)

- **`ph_exercise_log`** — daily morning-exercise routine log: `id, profile_id (FK → ph_profiles ON DELETE CASCADE), measured_at (timestamptz, server-stamped), total_calories (numeric), muscles (JSONB — distinct list worked), exercises (JSONB — per-exercise snapshot for history), created_at`. Indexed `(profile_id, measured_at DESC)`. Migration `016_exercises.sql`. Retention: **forever + `protected=true`** (set in the migration). **The routine DEFINITIONS are GLOBAL** in `dashboard_settings.medical.exercises` `{enabled, schedule:{time_hm}, items:[{id,name,reps,cal_per_rep,muscles[],other,include}]}` (edited on **Medical → Settings → 🏋️ Morning Exercises**). One row is written here per **✓ Done** (card) or per **reminder Clear**, computed from the include-✓ items by **`BOILER/dashboard/lib-exercise-log.js`** (`logExerciseRoutine(db, profileId)` — `total_calories = Σ reps × cal_per_rep`, muscles = distinct preset keys + non-empty `other`). Shared by `routes-personal-health.js` (Done) **and** `routes-reminders.js` (Clear) so the math never drifts.

All 6 measurement/schedule tables registered in `retention_policies` **and** in the Health → DB-Volumes view. DATE columns are returned as `YYYY-MM-DD` strings (`to_char`) to dodge the pg DATE timezone off-by-one.

## Daily steps (manual + walking-trip import)
A **👟 Daily steps** card in the same grid row as Log weight / Log blood pressure: a number input + **Save** (server-stamped) and a live **"Today: N steps (M from K walking trips)"** line, fed by `GET /steps`. Keyed by the selected person's `household_users.id` (so manual + trip entries share a key).

**Auto-import — SEGMENT-BASED classifier (rewritten 2026-06-27)** — `scripts/steps_from_trips.py` on **LXC 104**, cron `*/15`. For each confirmed, closed `phone_trips` row not yet imported, it **pulls the trip's actual GPS points** from `device_locations` (mapping `phone_trips.group_id → device_id` via the `dashboard_settings.geolocation` `tracked_devices`) and decides **walk / drive / phantom from PER-POINT segment speeds** — NOT the GPS-jitter-inflated `path_length_m` (which read a normal walk as "too fast" and couldn't tell a steady walk from drive→park→drive). Per consecutive pair it keeps only **good-accuracy segments** (both endpoints `accuracy_m ≤ accuracy_gate_m`, default 35) → `clean_m` (de-noised walked distance) + a list of segment km/h. Classify: **phantom** if `clean_m < phantom_min_m` (default 150) → skip; **driving** if `p85(speeds) > drive_kmh` (default 15) **OR** `≥ drive_run_segs` (default 3) consecutive segments `> drive_kmh` → skip (catches both a mostly-moving drive and a drive→park→drive burst); **too far** if `clean_m/1000 > walk_max_km` → skip; else **walking** → `steps = round(clean_m/1000 × steps_per_km)`, `measured_at = trip.returned_at`, mapped to a member by `device_label → household_users`. **Trips with no stored points (aged out / wiped, or group not mapped) are SKIPPED — never guessed.** Idempotent (partial-unique `trip_id` + NOT-EXISTS). Validated on a real walk (trip 13108, 2026-06-27): clean 2598 m, p85 ~8 km/h, max seg 13.7 (0 > 15) → walking → 3507 steps (vs the old jitter guess 2937). The plan/old-jitter history is in memory [[project_steps_segment_classifier]]. (Only Vadim's phone produces trips today; Maya gets trip-steps once her phone is OwnTracks-tracked.)

**Reconcile each run** — before importing, `DELETE FROM ph_steps WHERE source='trip' AND NOT EXISTS (… phone_trips …)` drops any trip-step whose trip the `geo_trip_janitor` (LXC 104, `*/5`) later deleted, keeping `ph_steps` trip rows in sync with the authoritative `phone_trips` set. (The **pre-2026-06-27 method** — `path_length_m/duration` speed window + a `min_trip_dist_m` / jitter-% discount — is gone; the segment classifier supersedes both the speed-window and the phantom-distance filter. Old `ph_steps` rows from that era keep their values until manually edited/removed; trips whose points have since aged out can't be recomputed.)

**Timezone (2026-06-26):** all three history lists + the "✓ saved" status (weight / BP / steps) render `measured_at` via `to_char(measured_at AT TIME ZONE 'Asia/Jerusalem', …)` — the pg session is `Etc/UTC`, so the bare `to_char` showed times 3 h behind local (e.g. a 09:59 trip read 06:59) while the "Today" total — which already converted — was right. The 6 `GET`/`POST` renders in `routes-personal-health.js` now convert. Stored instants are true UTC (OwnTracks `tst` epoch; manual saves = `now()`); only the **display** was wrong. The `+Add`/Edit round-trip is symmetric: `_histTs` builds a UTC ISO from the local date+time, display converts back. (Tests tab renders `tested_at` browser-side via `new Date(iso).toLocaleDateString` — different method, also correct.)

**Medical → Settings tab** edits the thresholds, stored in `dashboard_settings.medical.steps`: `steps_per_km` (def 1300), **`accuracy_gate_m`** (def 35), **`phantom_min_m`** (def 150), **`drive_kmh`** (def 15), `walk_max_km` cap (def 30), **`history_limit`** (def 10). (`drive_run_segs` def 3 is a code default, not surfaced.) Read by the watcher each run. The old `walk_min_kmh`/`walk_max_kmh`/`jitter_pct` knobs were removed 2026-06-27 with the speed-window method. (Manual + trip steps both add to the daily total — by design; if the manual number comes from a phone pedometer it already includes the walks, so that's a deliberate double-count the user accepts.)

**History modal (view / edit / remove — all three cards, 2026-06-26):** a **🕓 icon** on each of **Log weight**, **Log blood pressure**, **👟 Daily steps** opens a shared modal (`#ph-hist-modal`, JS `HIST`/`phHistory`/`phHist*` in `personal-health.js`) listing the **last N entries** (N = `history_limit`) for the selected person, each with inline **Edit** + **✕ remove**, plus a **"+ Add"** form that accepts a **chosen timestamp** (date + time, default now → ISO) for backdating / re-adding. **Trip-derived step entries are fully editable** (the km→steps calc isn't always right; the importer never overwrites an existing row, so an edit sticks) **and removable** — deleting a trip entry inserts its `trip_id` into **`ph_steps_excluded_trips`** so `steps_from_trips.py` won't re-import it (`AND t.id NOT IN (SELECT trip_id FROM ph_steps_excluded_trips)`). Backing endpoints (all in `routes-personal-health.js`): weight `GET /measurements?…&limit=` + `PATCH /measurements/:id` + `DELETE`; BP `GET /bp?profile_id=&limit=` + `PATCH /bp/:id` + `DELETE`; steps `GET /steps/list?user_id=&limit=` + `PATCH /steps/:id` + `DELETE /steps/:id` (the delete adds the trip exclusion). All three `POST`s accept an optional `measured_at` (ISO) for the timestamped add. New table **`ph_steps_excluded_trips`** (`trip_id PK, excluded_at`) — migration `011_steps_excluded.sql`. Retention **forever** + registered in **Health → DB-Volumes** (`tsCol = excluded_at`) since 2026-06-26.

## Computed metrics (front-end, `personal-health.js`)
- **Age** = years from `date_of_birth`
- **BMI** = `weight_kg / (height_cm/100)²`; **category** color-coded (Underweight `#e67e22` / Normal `#2e7d32` / Overweight `#e67e22` / Obese `#c0392b`)
- **Ideal weight** range = BMI 18.5–24.9 mapped to kg for the person's height
- **WHR** = latest `waist_cm ÷ hip_cm` (2 dp); **category** by sex (WHO: men Low `<0.90` / Mod `<1.00` / High; women Low `<0.80` / Mod `<0.85` / High), color-coded green/orange/red
