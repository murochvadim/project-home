### ⚠ HA Tuya integration can silently freeze — auto-reload in place
The HA **Tuya cloud** integration occasionally stops syncing: every Tuya entity's HA state freezes at one timestamp and HA commands become no-ops, while non-Tuya integrations (HomeKit/Z-Wave/SmartThings/Shelly) stay live. Symptom seen 2026-07-20: the **8 Gang Switch AWAY button dead** (AWAY = DPS 8 is **cloud-only**, so it fully depends on this path; HOME/ABROAD are local relays and kept working) + **boiler valve control blind** (`raw_data.valve_state` is read from the frozen HA entity, so the boiler agent couldn't see the valve's real state — which was physically ON). **Fix = reload the integration** (HA → Settings → Devices & Services → Tuya → ⋮ → Reload; if that doesn't restore it, re-authenticate — one-timestamp freeze = Tuya IoT Cloud token/subscription expiry). **Auto-recover:** HA automation **"Tuya Integration Reload"** (`automation.reload_tuya_integration_auto_recover`) runs **daily 04:00**, calling `homeassistant.reload_config_entry` on Tuya entry `01JJ6F8S69NZACDBP7Z6QV36K1` (targeted by entry-id). **Debug trap:** during a Tuya freeze, never infer a device's physical state from HA-fed data (`raw_data`, HA entity states) — check the LOCAL device row (`tcp_push` / `devices.last_state`). See memory `incident_tuya_integration_freeze`.

Polls `/api/health/network-integrations` every 60s. **Severity filter:** the badge counts only `severity != 'info'` — `info` is reserved for "pending drift detection" markers that the watchdog uses to track when a device first entered a drifted state; they promote to `warn` and start driving the badge red only after the maturity threshold (currently 6h for `network:device_cloud_only`). Clicks → Project Network page, where the same alerts render in detail (System Alerts card at the top of the page, filtered to `alert_type LIKE 'network:%'` via `GET /api/health/alerts?type_prefix=network:`). Four checks fire today: (a) `network:device_cloud_only:<dev_id>` — `protocol='local'` device whose `last_source` has been on a cloud channel (`ha_api` / `cloud_poll`) for ≥ 6h, meaning the local TCP/push channel is broken (caught the 2026-05-11 Kitchen Proximity Switch incident where the device sat on a different network for weeks, controllable via Tuya cloud but completely invisible to the local stack). Gateway sub-devices behind a Tuya WiFi gateway are EXCLUDED (they have no direct local TCP path — `cloud_poll` is their normal state). IR remotes with `last_source='keepalive'` are also excluded (their heartbeat IS the local stack working). (b) `network:lan_silent:<dev_id>` — device's `mac` is set but the matching `net_devices` row hasn't been refreshed by ARP scan in > 7 days (or doesn't exist at all). (c) `network:stale_local:<dev_id>` — device's `last_source` still claims `local_poll`/`tcp_push`/`gateway_push` but its `last_seen` is > 6h ago: the channel is frozen even though it didn't formally flip to cloud. Closes the blind spot where `device_cloud_only` would not fire because the source hasn't changed. (d) `network:ip_collision:<ip>` — two distinct MACs both seen within the last 10 min at the same IP. Distinct from DHCP-reassignment churn (where the previous occupant goes silent within seconds); here we observe two device radios answering simultaneously, which causes command drops + ARP cache thrash. Keyed by IP, not MAC — one alert per colliding IP regardless of how many MACs collide. Cloud-by-design protocols (`cloud`, `zwave`, `ring`, `zigbee`, `esp`, `awtrix`, `hasp`, `pixoo`, `alexa`, `vacuum`, `virtual`, `home_connect`, `mqtt`) are excluded from `device_cloud_only` and `lan_silent`; `stale_local` is gated to `protocol='local'` only; `ip_collision` is protocol-agnostic. **Manual-resolve semantics:** clicking "resolve" on an alert just clears the row (sets `resolved_at`); the watchdog re-raises it on the next 5-min cycle if the underlying condition is still active. There is no "snooze" / "acknowledge" feature today — resolve is cleanup, not suppression. To actually silence an alert, fix the root cause (move colliding device to a different DHCP lease, factory-reset + re-pair a drifted device, etc.) and the watchdog's auto-resolve loop will close it cleanly.

## Rules Time-Travel Architecture

Rules on LXC 105 query `device_events` at any historical timestamp to get accurate state — they do NOT rely on MQTT payload context or in-memory timers for historical judgment.

**Data access helpers in `RULES/state_manager.py`:**
- `get_device_state_at(device_id, at_ts)` — latest dps for device at or before ts
- `get_last_transition_before(device_id, dps_key, at_ts)` — most recent change
- `get_events_between(device_ids, from_ts, to_ts)` — raw events for any list of devices in range
- `db_execute()` returns rowcount; logs warning on 0-row UPDATE/DELETE (silent data-loss guard)

**Split DB connection (2026-04-14):** state_manager holds two connections — `self.conn` (+ `_db_lock`) for rule-driven ops (db_execute, db_query, emit_virtual_event, get_* helpers), and `self._hb_conn` (+ `_hb_lock`) exclusively for the heartbeat thread (load_from_db, load_shared_state, save_shared_state, _write_heartbeat). Prevents `save_shared_state`'s 167-row upsert (~200ms) from blocking rule emissions. Max emission time dropped from 225-255ms to 2-6ms.

**Virtual devices** — derived states from rules live in `device_events` too, using `virtual:<name>` id prefix. Registered in `devices` table (device_type='virtual', protocol='virtual') so they appear on dashboard. Rules emit via `state.emit_virtual_event(virtual_id, dps, source, ...)` which dedupes against prior state.

Current virtual devices:
- `virtual:home_activity` (owner: Home Activity rule) — legacy: `active_rooms`, `activity_level`, `active_room_count`, `last_motion_room`; **apartment-vision (2026-04-24):** `active_zones`, `active_zone_count`, `last_motion_zone`, `door_state` (map of door-name → 'open'|'closed')
- `virtual:people_home` (owner: People Home rule) — legacy: `people_home`, `home_mode`, `someone_home`, `occupied_rooms`; **apartment-vision (2026-04-24):** `people_confidence` (high|medium|low|**transit**|**recalculating**), `last_entered_via`, `last_exited_via`, `last_transition_ts`, `people_count_state` (**stable**|**transit**|**recounting**), `people_count_floored`, `people_count_high_water`, `people_count_live`, `last_transition_source` (`door_sensor` | `inferred_entry` | `inferred_exit`)
- `virtual:boiler_status` (owner: Boiler Consumption Classify) — `last_cause`, `last_drop_c`, `last_rooms`, `last_start_ts`
- `virtual:corridor_transit` (owner: Corridor Transit Classifier, added 2026-05-27) — `mode` (`Corridor_Clear_Home` / `Corridor_Visit_Home` / `Corridor_To_Home` / `Corridor_From_Home`), `prior_mode`, `mode_set_ts`. Classifies apartment ↔ corridor movement by time-correlating Corridor Presence, Main Door open/close, and Entrance Presence events

**Apartment-vision upgrade (2026-04-24):** Home Activity + People Home now consume `state.spatial` — a zone/adjacency/sub-rooms index built by `state_manager.load_from_db()` from `dashboard_settings.room_layouts.*` + `room_device_placements`. Each sensor placement gets `zones` (full cone coverage) + `primary_zone` (zone at beam midpoint) — activity uses primary_zone to avoid edge-overlap false activations.

**Room classification in People Home counting (2026-04-24):**
- **Sub-room folding**: Kitchen auto-folded via zone-name heuristic; Dining Room + Entrance manually folded via `DEFAULT_MANUAL_SUBROOM_MERGE` (their parent zones named "Dining Table" / separate layout don't match the auto heuristic). All fold to Living Room — the open-plan living area counts as 1 room, not 4.
- **Transit-only rooms (`DEFAULT_TRANSIT_ROOMS`)**: Hallway. Walked through but not counted. Still shows in `active_rooms` / `occupied_rooms` (so the dashboard lights up Hallway when someone walks through) but excluded from `presence_rooms` / `people_count`.
- **Exterior (`DEFAULT_EXTERIOR_ROOMS`)**: Corridor (building hallway outside flat). Excluded entirely from count; used as Tier-1 signal for inferred transit.
- **Exterior motion**: Ring Doorbell (camera at Main Door). Same treatment — Tier-1 signal, not counted.
- **Counted rooms**: Living Room (open-plan parent), Balcony (separate room via sliding door), Bedroom, My BathRoom, Guy Room, DressRoom, Bathroom, Laundry, BedRoom Balcony.

**High-water people count since last Main Door close (2026-05-13 — replaces the prior Constant/Dynamic split):** `people_home` is a **single** value computed as the running maximum of the live sustained-zone count between Main Door close events. Two visual states only:

| state | trigger | dashboard | confidence |
|---|---|---|---|
| `transit` | Main Door `open` | `--` (amber italic) | `transit` |
| `stable` | Main Door closed (normal operation) | integer | `high` / `medium` / `low` |

Flow on every event:
1. Build `sustained_zones` from `state.shared['active_zones']`: drop transit zones (doorways / walkways), drop zones owned by exterior / transit rooms (Corridor / Hallway), require each remaining zone to be continuously active ≥ `zone_sustained_sec` (default 30 s, 15 s flicker tolerance via `ZONE_GAP_TOLERANCE_SEC`).
2. **Per-room cap of 1:** group `sustained_zones` by owner room and count each room once → `counted_rooms`. `live_count = len(counted_rooms)`. Defends against overlapping FP2 zone polygons (a single person at a zone boundary registers in 2-3 zones simultaneously). Future opt-in `multi_target_rooms` knob (not yet implemented) will disable the cap for rooms with physically-disjoint zones.
3. **Settle gate before high-water rises:** `people_home` only bumps to a higher value once `live_count` has stayed above the current high-water for ≥ `count_settle_sec` (default 60 s). Tracked via `_was_above_high_water` (bool) + `_count_above_high_water_since` (timer). Filters transient peaks (e.g. one person walking room-to-room — Balcony stays sustained during the hold-off tail while Living Room becomes sustained → live_count momentarily = 2 → without the settle gate, the high-water absorbs 2 and locks until the next door close). The gate makes the algorithm tolerant of normal movement while still catching genuine sustained 2-person scenarios.
4. **Only** decrease path: Main Door rising-edge close (open → closed) **after the door was open for ≥ `main_door_min_open_sec`** (default 3 s, filters accidental brief opens). On reset: `people_home = live_count` (bypasses the settle gate — the door close re-establishes ground truth). `_was_above_high_water` cleared. Inferred Tier-1↔Tier-3 transit (Corridor / Ring Doorbell ↔ Entrance presence, within `transit_sequence_window_sec`) classified as `exit` triggers the same reset path — handles a dead Main Door sensor.

The invariant **"the Main Door is the only way to leave the apartment"** is what justifies this design: between Main Door close events the count can ONLY grow (new sustained zones reveal previously-undetected occupants). On door close the apartment is sealed and the live count is, by definition, the ground truth.

- Consume state → use the 3 helpers; never trust MQTT payload for historical state

- Writes that matter → check rowcount return from `db_execute`
- Scaling → prefer specific `triggers=["device_id", ...]` over wildcard `["*"]`; for wildcard rules, filter + early-return in first 2 lines

So one rule's slow/unreachable-device call held the lock for seconds and **queued every incoming event behind it** — measured as intermittent **9–13 s** delays before an unrelated rule (e.g. My Bathroom Lights presence) even processed its event. Fix: rules now **enqueue** commands (`self._dispatch_queue.put((cmd, rule_name))`) under the lock — fast, in-memory — and a single daemon **`dispatch-worker`** thread (`_dispatch_worker_loop`, started in `run()`) drains the queue and runs `_dispatch_command` **off** the lock. Single worker → global FIFO command order preserved. Thread-safe by construction: `_check_loop`→`_disable_rule` already takes `_dispatch_lock`, mutually excluded from the firing thread's `state.shared` copies; `run_scene`/`_delay_sec` already dispatched off-thread. A throttled WARNING logs if the queue depth exceeds 200 (a target device is slow/unreachable; self-drains on recovery). **Side effect:** the rules-table **Dispatch** column now reads ~evaluate-only time (device I/O moved off-cycle) — correct, since the rule's real blocking cost IS now just its evaluate. Verified: presence→light dropped from 9–13 s to **~2 s** (the ~2 s is now purely the Tuya relay hardware round-trip, not the engine). **Resource note:** LXC 105 is NOT resource-bound — measured 97% idle CPU (1 core, Ryzen 9 host), 35 MB RSS / 512 MB, 0 swap, DB RTT ~0.03 ms (same-host LXC-to-LXC). Adding cores/RAM does nothing (single-process, GIL-bound, idle); the dispatch-lock stall was the only real bottleneck and it's fixed. Engine-core change → needs `systemctl restart rule-engine`.
- **Batched `save_shared_state` (2026-06-12):** `state_manager.save_shared_state` now does ONE `execute_values` multi-row upsert instead of ~167 sequential `cur.execute` round-trips (measured 9.3 ms → 1.0 ms, 9×). Matters because this save is also called per-event from the dispatch path when shared state changed (rule_engine ~L638) while holding the lock — so the hold drops to ~1 ms. (The old docstring claimed "200-300 ms" but that was wrong for this deployment: same-host DB RTT ~0.03 ms made 167 round-trips only ~9 ms — a DB-write worker was considered and **rejected** as not worth the complexity for an ~8 ms win.
