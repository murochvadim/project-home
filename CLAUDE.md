- **Network Integration badge** (full row, below Device Integration, since 2026-05-12): `Network Integration ✓` (green) / `Network Integration ✗ N alerts` (dark red) — active `network:*` alerts from the per-device reachability checks in the same LXC 104 watchdog. Polls `/api/health/network-integrations` every 60s. **Severity filter:** the badge counts only `severity != 'info'` — `info` is reserved for "pending drift detection" markers that the watchdog uses to track when a device first entered a drifted state; they promote to `warn` and start driving the badge red only after the maturity threshold (currently 6h for `network:device_cloud_only`). Clicks → Project Network page, where the same alerts render in detail (System Alerts card at the top of the page, filtered to `alert_type LIKE 'network:%'` via `GET /api/health/alerts?type_prefix=network:`). Four checks fire today: (a) `network:device_cloud_only:<dev_id>` — `protocol='local'` device whose `last_source` has been on a cloud channel (`ha_api` / `cloud_poll`) for ≥ 6h, meaning the local TCP/push channel is broken (caught the 2026-05-11 Kitchen Proximity Switch incident where the device sat on a different network for weeks, controllable via Tuya cloud but completely invisible to the local stack). Gateway sub-devices behind a Tuya WiFi gateway are EXCLUDED (they have no direct local TCP path — `cloud_poll` is their normal state). IR remotes with `last_source='keepalive'` are also excluded (their heartbeat IS the local stack working). (b) `network:lan_silent:<dev_id>` — device's `mac` is set but the matching `net_devices` row hasn't been refreshed by ARP scan in > 7 days (or doesn't exist at all). (c) `network:stale_local:<dev_id>` — device's `last_source` still claims `local_poll`/`tcp_push`/`gateway_push` but its `last_seen` is > 6h ago: the channel is frozen even though it didn't formally flip to cloud. Closes the blind spot where `device_cloud_only` would not fire because the source hasn't changed. (d) `network:ip_collision:<ip>` — two distinct MACs both seen within the last 10 min at the same IP. Distinct from DHCP-reassignment churn (where the previous occupant goes silent within seconds); here we observe two device radios answering simultaneously, which causes command drops + ARP cache thrash. Keyed by IP, not MAC — one alert per colliding IP regardless of how many MACs collide. Cloud-by-design protocols (`cloud`, `zwave`, `ring`, `zigbee`, `esp`, `awtrix`, `hasp`, `pixoo`, `alexa`, `vacuum`, `virtual`, `home_connect`, `mqtt`) are excluded from `device_cloud_only` and `lan_silent`; `stale_local` is gated to `protocol='local'` only; `ip_collision` is protocol-agnostic. **Manual-resolve semantics:** clicking "resolve" on an alert just clears the row (sets `resolved_at`); the watchdog re-raises it on the next 5-min cycle if the underlying condition is still active. There is no "snooze" / "acknowledge" feature today — resolve is cleanup, not suppression. To actually silence an alert, fix the root cause (move colliding device to a different DHCP lease, factory-reset + re-pair a drifted device, etc.) and the watchdog's auto-resolve loop will close it cleanly.

## Rules Time-Travel Architecture

Rules on LXC 105 query `device_events` at any historical timestamp to get accurate state — they do NOT rely on MQTT payload context or in-memory timers for historical judgment.

**Data access helpers in `RULES/state_manager.py`:**
- `get_device_state_at(device_id, at_ts)` — latest dps for device at or before ts
- `get_last_transition_before(device_id, dps_key, at_ts)` — most recent change
- `get_events_between(device_ids, from_ts, to_ts)` — raw events for any list of devices in range
- `db_execute()` returns rowcount; logs warning on 0-row UPDATE/DELETE (silent data-loss guard)

**Split DB connection (2026-04-14):** state_manager holds two connections — `self.conn` (+ `_db_lock`) for rule-driven ops (db_execute, db_query, emit_virtual_event, get_* helpers), and `self._hb_conn` (+ `_hb_lock`) exclusively for the heartbeat thread (load_from_db, load_shared_state, save_shared_state, _write_heartbeat). Prevents `save_shared_state`'s 167-row upsert (~200ms) from blocking rule emissions. Max emission time dropped from 225-255ms to 2-6ms.

**Virtual devices** — derived states from rules live in `device_events` too, using `virtual:<name>` id prefix. Registered in `devices` table (device_type='virtual', protocol='virtual') so they appear on dashboard. Rules emit via `state.emit_virtual_event(virtual_id, dps, source, ...)` which dedupes against prior state.

Current virtual devices:
- `virtual:home_activity` (owner: Home Activity rule) — legacy: `active_rooms`, `activity_level`, `active_room_count`, `last_motion_room`; **apartment-vision (2026-04-24):** `active_zones`, `active_zone_count`, `last_motion_zone`, `door_state` (map of door-name → 'open'|'closed')
- `virtual:people_home` (owner: People Home rule) — legacy: `people_home`, `home_mode`, `someone_home`, `occupied_rooms`; **apartment-vision (2026-04-24):** `people_confidence` (high|medium|low|**transit**|**recalculating**), `last_entered_via`, `last_exited_via`, `last_transition_ts`, `people_count_state` (**stable**|**transit**|**recounting**), `people_count_floored`, `people_count_high_water`, `people_count_live`, `last_transition_source` (`door_sensor` | `inferred_entry` | `inferred_exit`)
- `virtual:boiler_status` (owner: Boiler Consumption Classify) — `last_cause`, `last_drop_c`, `last_rooms`, `last_start_ts`

**Apartment-vision upgrade (2026-04-24):** Home Activity + People Home now consume `state.spatial` — a zone/adjacency/sub-rooms index built by `state_manager.load_from_db()` from `dashboard_settings.room_layouts.*` + `room_device_placements`. Cone-to-zone geometry (point-in-polygon, 1m cells) ported from `buildApartmentScene` in server.js. Each sensor placement gets `zones` (full cone coverage) + `primary_zone` (zone at beam midpoint) — activity uses primary_zone to avoid edge-overlap false activations.

**Room classification in People Home counting (2026-04-24):**
- **Sub-room folding**: Kitchen auto-folded via zone-name heuristic; Dining Room + Entrance manually folded via `DEFAULT_MANUAL_SUBROOM_MERGE` (their parent zones named "Dining Table" / separate layout don't match the auto heuristic). All fold to Living Room — the open-plan living area counts as 1 room, not 4.
- **Transit-only rooms (`DEFAULT_TRANSIT_ROOMS`)**: Hallway. Walked through but not counted. Still shows in `active_rooms` / `occupied_rooms` (so the dashboard lights up Hallway when someone walks through) but excluded from `presence_rooms` / `people_count`.
- **Exterior (`DEFAULT_EXTERIOR_ROOMS`)**: Corridor (building hallway outside flat). Excluded entirely from count; used as Tier-1 signal for inferred transit.
- **Exterior motion**: Ring Doorbell (camera at Main Door). Same treatment — Tier-1 signal, not counted.
- **Counted rooms**: Living Room (open-plan parent), Balcony (separate room via sliding door), Bedroom, My BathRoom, Guy Room, DressRoom, Bathroom, Laundry, BedRoom Balcony.

**High-water people count since last Main Door close (2026-05-13 — replaces the prior Constant/Dynamic split):** `people_home` is a **single** value computed as the running maximum of the live sustained-zone count between Main Door close events. Two visual states only:

| state | trigger | dashboard | confidence |
|---|---|---|---|
| `transit` | Main Door `open` | `--` (amber italic) | `transit` |
| `stable` | Main Door closed (normal operation) | integer | `high` / `medium` / `low` |

Flow on every event:
1. Build `sustained_zones` from `state.shared['active_zones']`: drop transit zones (doorways / walkways), drop zones owned by exterior / transit rooms (Corridor / Hallway), require each remaining zone to be continuously active ≥ `zone_sustained_sec` (default 30 s, 15 s flicker tolerance via `ZONE_GAP_TOLERANCE_SEC`).
2. **Per-room cap of 1:** group `sustained_zones` by owner room and count each room once → `counted_rooms`. `live_count = len(counted_rooms)`. Defends against overlapping FP2 zone polygons (a single person at a zone boundary registers in 2-3 zones simultaneously). Future opt-in `multi_target_rooms` knob (not yet implemented) will disable the cap for rooms with physically-disjoint zones.
3. **Settle gate before high-water rises:** `people_home` only bumps to a higher value once `live_count` has stayed above the current high-water for ≥ `count_settle_sec` (default 60 s). Tracked via `_was_above_high_water` (bool) + `_count_above_high_water_since` (timer). Filters transient peaks (e.g. one person walking room-to-room — Balcony stays sustained during the hold-off tail while Living Room becomes sustained → live_count momentarily = 2 → without the settle gate, the high-water absorbs 2 and locks until the next door close). The gate makes the algorithm tolerant of normal movement while still catching genuine sustained 2-person scenarios.
4. **Only** decrease path: Main Door rising-edge close (open → closed) **after the door was open for ≥ `main_door_min_open_sec`** (default 3 s, filters accidental brief opens). On reset: `people_home = live_count` (bypasses the settle gate — the door close re-establishes ground truth). `_was_above_high_water` cleared. Inferred Tier-1↔Tier-3 transit (Corridor / Ring Doorbell ↔ Entrance presence, within `transit_sequence_window_sec`) classified as `exit` triggers the same reset path — handles a dead Main Door sensor.

The invariant **"the Main Door is the only way to leave the apartment"** is what justifies this design: between Main Door close events the count can ONLY grow (new sustained zones reveal previously-undetected occupants). On door close the apartment is sealed and the live count is, by definition, the ground truth.

**Removed in the 2026-05-13 rewrite:** `people_home_dynamic` (was Constant + discoveries), `_people_locked_count`, `_people_lock_zones`, `_recount_max_zones`, `_recalc_pending`, `_post_door_stabilize`, `_people_discovered_*`, `zone_accounted:*` timers, `people_count_state='recounting'`, and the auto-sized stabilize window (no window anymore). **Switch-retain suppression (2026-04-23):** Home Activity's switch dispatch path now only fires `room_active:*` + `room_interact:*` timers when the switch state *signature* (dps keys excluding `last_seen`/`linkquality`/`battery`/etc.) differs from the previous signature. (3) **TX-510 omits the 32-byte user_name slot** from IDENT/REG_USER responses that newer HLK-FRM v1.0.3 firmware echoes back, so the ESP maintains its own local id→name table in EEPROM (offset 65..3264, 100 slots × 32 bytes). On REG_USER success the sketch captures `esp_params.pending_user_name` and writes it to slot `[user_id]`; on IDENT success it reads `last_user_name` back from the same slot so the dashboard's `last_recognition` field shows `<name> (<id>)` instead of just `user_<id>`. (4) TX-510 does NOT support `demo_mode` / `query_state` / `query_uuid` — these were removed from the schema. (5) **5-way enrolment (`REG_USER_5WAY` 0x26) confirmed unsupported on V1.00.0006** — 2026-05-14, 10 attempts sent, zero responses. PDF revision history shows 0x26 was added/modified in v1.0.0+ firmware after this hardware was manufactured. Code paths for 0x26 were stripped 2026-05-14; only `REG_USER` (0x13, one-shot) remains. **Sketch identity:** `sketch_name="Face_Recognition_ESP8266"` (must contain "ESP8266" so dashboard's OTA chip detection picks port 8266 over 3232), `sketch_version="v12"`. **EEPROM layout:** 0..31 HA-IP legacy, 32 magic (`0xB3`), 33..64 `pending_user_name`, 65..3264 user-name table (100×32). Magic-byte change resets all params to defaults on first boot. **Door-unlock chain (preserved from legacy sketch):** FR board publishes `face_identified {user_id, user_name, ts}` to `mur/home/esp/face_01/event`; the RemoteXY board (another esp_boards peer) subscribes and triggers door unlock independently — no random_key echo from this board. **Dashboard surface:** Project Boards page → Face Recognition tab. Simulation tab has 2 cards: `Face Recognition` (Start Recognition / Reboot FR Module + `Last Recognized` + `Enrolled Users` live status fields) + `Face Module Controls` (Screen On/Off / Flash On/Off + `Screen` live status field). Params tab has the Enrolled Users table (per-row 🗑 Delete that POSTs `delete_user:<id>`) + form for `pending_user_name` + `[Save Parameters]` + `[▶ Register User]` buttons side-by-side (Register User uses the same dispatch as a Simulation-tab action button, just surfaced next to Save so the natural flow stays in one place; the dashboard's `SURFACED_ELSEWHERE` set keeps it out of the fallback "Other" card). Onboarding flow: set pending_user_name in Params → Save → click ▶ Register User → present face → board enrolls + writes name to local table → `face_register_success` event fires + status refreshes. **Known operational quirk:** FAIL2D (status `0x06`) on REG_USER means face wasn't captured cleanly — usually screen off, bad lighting, or face too close/far. Screen MUST be on for enrolment; setup() boots with screen off so the FR display doesn't draw current when not in use.

- **Dashboard MQTT auto-heal (since 2026-05-14):** `BOILER/dashboard/server.js` now (a) fail-loud-exits at startup if `MQTT_RULE_PASS` is missing from the env (no more silent "Not authorized" retry loops where button clicks API-succeed but never reach the broker), (b) prints a clearly framed diagnostic box on the 3rd consecutive auth failure naming both likely causes (transient mqtt-js bug vs real password mismatch), and (c) **auto-heals** by tearing down the stuck mqtt client (`end(true)` + remove all listeners) and creating a fresh `mqtt.connect()` after 3 auth fails (≈15 s), capped at one heal per 30 s. Triggered by an observed mqtt-js v5.15.1 bug where the reconnect-after-keepalive-timeout path gets into a state mosquitto rejects, even though credentials never changed. Python `paho-mqtt` clients hitting the same broker never reproduce — they reconnect cleanly every time — so the fix is specifically a Node.js workaround. Recovery log line `MQTT recovered after N failed attempts` appears in pm2 logs on every successful heal. Net effect: a previously 11-minute dashboard outage when this triggers drops to ~15-20 s.

- **Aqara FP2 integration (since 2026-05-12):** the Living Room FP2 (id `fp2_presence_335e`, MAC ending `335E`) is paired via **HomeKit Controller** in HA (not Matter, not Tuya — Aqara's app pairs the FP2 to Apple HomeKit, and HA discovers the HAP accessory via mDNS). The device row uses `protocol='homekit'` — a generic protocol category introduced alongside FP2 for any HA-mediated HomeKit Controller device. `homekit` is in `_CLOUD_BY_DESIGN_PROTOCOLS` on the watchdog (LXC 104) so it is excluded from `network:device_cloud_only` / `network:lan_silent` / `network:stale_local` drift checks (HA WS is the canonical channel, no local TCP path expected). Dashboard surface: `.proto-homekit` badge color `#d63384`, `isOnline()` branch matches ring/zwave shape (`last_state ? true : ageSec < 600`), HomeKit option in both `filter-proto` and `settings-proto` dropdowns, dedicated `stat-homekit` chip in the protocol stats strip. To bring its state into the project, the FP2 reuses the `HA_DIRECT_DEVICES` pattern from the vacuum integration: one `devices` row (`device_type='presence'`, `protocol='homekit'`) pulls from **8 HA entities** simultaneously — `binary_sensor.presence_sensor_fp2` (global presence) + 6 per-zone binary sensors (one per zone the user drew in the Aqara Home app — `Balcony Doorway`, `Dining Table`, `Kitchen Bar`, `Kitchen Cooking`, `Kitchen Walkway`, `Sofa Entertaiment`) + `sensor.presence_sensor_fp2_335e_light_sensor_light_level` for illuminance. Each entity projects into its own DPS key (`presence`, `z_balcony_doorway`, …, `z_sofa_entertaiment`, `illuminance`); zone names are declared in the row's `dps_labels` jsonb. The 6 zones cover the *named* zones synced from Aqara's HomeKit export; HomeKit appears to cap zone exports at 6, so the apartment layout's `Tv Wall`, `Hallway Walkway`, `Corridor Doorway` are NOT exposed today — Living Room layout treats those as "covered by global presence" until more zones can be exposed. No Matter integration is used; Aqara's "Scene and Signal Sync" Matter-export feature is for *derived* custom signals (combinations of conditions), not the raw FP2 device, so it does not apply here. HomeKit pairing on Aqara FP2 needs the FP2 to be set up via the Aqara app on **Android** (or removed from Apple Home if originally set up via iPhone) — once free, HA's HomeKit Device integration auto-discovers it on the LAN and pairs with the device's 8-digit HomeKit code (shown on the physical sticker AND in Aqara Home → FP2 → Settings → Apple HomeKit).

### Project Health Page (sidebar: General → Project Health)

Counted by the sidebar Status badge alongside the other infra checks (added 2026-04-29).
  - **Server**: `pm2` — all pm2 processes online
  - **Services**:
    - `boiler_agent` — boiler service on LXC 103 (via `system_alerts`: red if active `service_down`/`service_ssh_failed`)
    - `media_agents` — analyzer, player, ingest on LXC 100 (via `system_alerts`: shown as 3 inline dots)
    - `voice_agent` — whisper-http on LXC 106 (via `system_alerts`: red if active `service_down`/`service_ssh_failed`)
  - **Scripts / Ingest** (direct DB/SSH checks):
    - `wf96c_ingest` (dashboard key still `ha_to_pg` for back-compat) — age of last `raw_data` row ≤ 15 min (DB query). Source switched from HA-polling cron to event-driven MQTT consumer on 2026-04-23; see [BOILER/CLAUDE.md](BOILER/CLAUDE.md#data-flow).
    - `collect_weather` — age of last `raw_weather` row ≤ 65 min (DB query)
    - `auto_scan` — age of `/var/log/auto_scan.log` on LXC 100 ≤ 120 s (SSH)
  - **Data freshness** (DB queries):
    - `boiler_last_decision` — age of last `agent_boiler_data` row ≤ `run_interval_min × 3`; shows age + decision
    - `orchestrator_last_run` — age of last `orchestrator_log` row ≤ 70 min; shows age
    - `active_alerts` — count of unresolved `system_alerts`; shows worst severity
- **Orchestrator Log card**: last N entries from `orchestrator_log` table; severity colour-coded (info/warn/error); shows last run time + status summary; `GET /api/health/orch-log?limit=N`
- **DB Volumes card**: table row counts, disk size, dead tuples, frag %, last vacuum per table; fetched from `/api/health/db-volumes` using `pg_stat_user_tables`; each row has a **Vacuum** button — runs `VACUUM ANALYZE` and updates dead tuples + frag % inline. **Adding a new table to the view requires two edits in the `/api/health/db-volumes` handler in `server.js`**: append the table name to the `tables` array AND add a `tsCol[<table>] = '<timestamp_col>'` entry (or `null` if the table has no time column) so the oldest/newest range query works. The `new-DB-table-alert` post-tool hook nudges this on every new `CREATE TABLE`, but the handler is the source of truth — neither retention_policies seed nor the table existing in pg is enough on its own.
- **Retention Policies card**: editable table per DB table — keep_days (blank = forever), auto_clean toggle, clean_interval_hours, last_cleaned timestamp; Save per row, Clean per row, "Clean All Now" global button
  - Policies stored in `retention_policies` DB table (not config file — so orchestrator reads/writes them programmatically)
  - Default policies seeded on first run: raw_data=90d, agent_boiler_data=365d, raw_weather=60d, raw_weather_daily=60d, boiler_consumptions=forever, orchestrator_log=30d, system_alerts=90d, sync_signals=7d
- **API endpoints:**
  - `GET /api/health/status` — checks PostgreSQL, HA, TCP to all LXCs, PM2; boiler-agent + media agents + voice agent (all via system_alerts); ha_to_pg + collect_weather freshness (DB); auto_scan log age (SSH); orchestrator last run age; boiler last decision age; active alerts count
  - `GET /api/health/orch-log?limit=N` — last N orchestrator log entries
  - `GET /api/health/db-volumes` — row counts + sizes + date ranges per table
  - `GET /api/health/retention` — all retention policies
  - `POST /api/health/retention` — update one policy `{table_name, keep_days, auto_clean, clean_interval_hours}`
  - `POST /api/health/cleanup` — run cleanup `{table_name}` (null = all); returns `{results:[{table_name, deleted}]}`
  - `POST /api/health/vacuum` — run `VACUUM ANALYZE {table_name}`; returns `{ok, dead_tup, frag_pct}` after
- **retention_policies table schema:** `table_name PK, keep_days INT nullable, auto_clean BOOL, clean_interval_hours INT, last_cleaned_at TIMESTAMPTZ, description TEXT`

### General Page / Weather (sidebar: General → Weather)
- **Today's Outlook card**: Solar Heating Potential (1–10) + Rain Probability (1–10) + Season; updated every 30 min
  - Scores computed on-the-fly in `/api/weather/scores` from latest `raw_weather` + today's `raw_weather_daily` — not stored in DB
  - Solar score: based on `condition` + `uv_index` (max of IMS and balcony); displayed as large colored number with description label (no icon)
  - Rain score: based on `condition` + `precipitation_mm` from today's forecast

- **Current Conditions card**: reads latest row from `raw_weather` (no HA token needed on Windows dashboard)
- **Hourly Weather Log table**: last 24/48/72 rows from `raw_weather`
- **Daily Forecast Log table**: last 14/30 rows from `raw_weather_daily` (precipitation in mm)
- API endpoints: `/api/weather/scores`, `/api/weather/latest`, `/api/weather/hourly`, `/api/weather/daily`
- `collect_weather.py` cron runs every 60 min on LXC 103 (`0 * * * *`)
